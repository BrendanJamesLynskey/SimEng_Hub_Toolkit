# Simulation Engineering Toolkit

The engineering around a simulator: the languages its fast paths are written in, the memory systems and RTL it must agree with, the tests, pipelines and trackers that keep it trustworthy, the specifications it is built to, and the front ends that feed it real workloads. Each deck is backed by a tested code repository, and every number in the decks comes from a recorded run.

**Live index:** https://brendanjameslynskey.github.io/SimEng_Hub_Toolkit/

## How this series relates to its sisters

[LLM Inference Simulators](https://github.com/BrendanJamesLynskey/LLM_Hub_Inference_Simulators) teaches how to build, validate and accelerate a simulator; [FHE Accelerator Simulators](https://github.com/BrendanJamesLynskey/FHE_Hub_Accelerator_Simulators) applies that to an FHE accelerator. This series covers the engineering practice around both: the languages a simulator's fast core is written in, the hardware it must agree with, and the tests, pipelines, trackers and specifications that make its answers trustworthy. Every number quoted in a deck comes from a recorded run (`examples/results.md` in the code repos), and every code snippet is taken from code that compiles and is tested.

## Glossary: concepts and where they are explained

Every concept the decks rely on, with links to the slides that explain it in depth. The same glossary, with anchors each deck links to, is on the [live index](https://brendanjameslynskey.github.io/SimEng_Hub_Toolkit/#glossary).

| Concept | What it is | Where it is explained |
|---|---|---|
| BinaryHeap and Reverse | Rust's standard priority queue is a max-heap; wrapping entries in std::cmp::Reverse makes it the min-heap an event list needs, so the earliest event pops first. Push and pop are O(log n). | [SimEng 01 · the event list](https://brendanjameslynskey.github.io/SimEng_01_Rust_for_Simulation_Engineers/#slide-02) |
| Total ordering of floats (total_cmp) | f64 is only partially ordered because NaN compares unequal to everything. f64::total_cmp implements IEEE 754 totalOrder, which lets float times key a heap. | [SimEng 01 · ordering floats, breaking ties](https://brendanjameslynskey.github.io/SimEng_01_Rust_for_Simulation_Engineers/#slide-03) |
| Deterministic tie-breaking | Events at equal times are ordered by priority (SimPy's URGENT before NORMAL) and then by a sequence number (first scheduled, first served), so the same inputs always give the same event order and the same answers. | [SimEng 01 · the ordering rule](https://brendanjameslynskey.github.io/SimEng_01_Rust_for_Simulation_Engineers/#slide-03); [SimEng 01 · interactive event queue](https://brendanjameslynskey.github.io/SimEng_01_Rust_for_Simulation_Engineers/#slide-04); [SimEng 03 · ties in SystemC](https://brendanjameslynskey.github.io/SimEng_03_SystemC_TLM_Models/#slide-08); [LLM Inference Simulators 02 · determinism pitfalls](https://brendanjameslynskey.github.io/InfSim_02_Simulator_Development_Tutorial/#slide-10) |
| Events as enums; exhaustive match | Events are plain data (an enum of small, copyable variants) and the model handles them in a match; the compiler rejects a match that forgets a variant. | [SimEng 01 · events as enums, models as traits](https://brendanjameslynskey.github.io/SimEng_01_Rust_for_Simulation_Engineers/#slide-05) |
| Ownership and borrowing | Every value has one owner; references borrow it, either shared (many readers) or exclusive (one writer), never both at once. The compiler enforces this, which rules out dangling references and data races. | [SimEng 01 · ownership in an event loop](https://brendanjameslynskey.github.io/SimEng_01_Rust_for_Simulation_Engineers/#slide-06); [The Rust Programming Language, chapter 4](https://doc.rust-lang.org/book/ch04-00-understanding-ownership.html) |
| Arenas and indices | The simulation owns all requests and instances in vectors; events and queues hold indices into them. Borrows last one statement, so the borrow checker is satisfied without Rc<RefCell>, and indices can be logged and replayed. | [SimEng 01 · ownership in an event loop](https://brendanjameslynskey.github.io/SimEng_01_Rust_for_Simulation_Engineers/#slide-06) |
| Processes as state machines | A SimPy process is a generator that sleeps at each yield. Without stable generators, Rust names those sleep points as states and lets each event resume the component from where it slept. | [SimEng 01 · from SimPy processes to state machines](https://brendanjameslynskey.github.io/SimEng_01_Rust_for_Simulation_Engineers/#slide-07) |
| Traits; static and dynamic dispatch | A trait is an interface. Generic code (<C: CostModel>) is compiled once per implementation and can inline calls; a trait object (Box<dyn CostModel>) chooses the implementation at run time through a vtable. | [SimEng 01 · traits for pluggable cost models](https://brendanjameslynskey.github.io/SimEng_01_Rust_for_Simulation_Engineers/#slide-08) |
| Result, ? and panic | Expected failures (a bad configuration) return Result and propagate with ?; broken invariants (an event in the past) panic!, stopping the run at the point of the bug. | [SimEng 01 · errors](https://brendanjameslynskey.github.io/SimEng_01_Rust_for_Simulation_Engineers/#slide-09) |
| rayon, Send and Sync | rayon turns iter() into par_iter() on a work-stealing thread pool. The Send and Sync traits let the compiler prove that what each thread touches is safe to share, so a data race is a compile error. | [SimEng 01 · fearless parallel sweeps](https://brendanjameslynskey.github.io/SimEng_01_Rust_for_Simulation_Engineers/#slide-10) |
| cargo, clippy and rustfmt | Rust's build tool, linter and formatter. cargo clippy -- -D warnings fails the build on any lint; cargo fmt --check enforces one layout. | [SimEng 01 · the toolchain](https://brendanjameslynskey.github.io/SimEng_01_Rust_for_Simulation_Engineers/#slide-11) |
| criterion benchmarks | A Rust benchmarking library: warm-up, many samples, confidence intervals and comparison with the previous run, so performance changes are measured rather than guessed. | [SimEng 01 · the toolchain](https://brendanjameslynskey.github.io/SimEng_01_Rust_for_Simulation_Engineers/#slide-11); [SimEng 06 · a performance gate in CI](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-13) |
| Amdahl's law for a port | Speeding up part of a program speeds up the whole only in proportion to that part's share of the time. After porting a simulator's engine, the Python code around it can dominate. | [SimEng 02 · interactive: what should you port?](https://brendanjameslynskey.github.io/SimEng_02_Rust_Python_PyO3/#slide-11); [SimEng 02 · what crosses the boundary](https://brendanjameslynskey.github.io/SimEng_02_Rust_Python_PyO3/#slide-04); [LLM Inference Simulators 08 · Amdahl's law for simulators](https://brendanjameslynskey.github.io/InfSim_08_Accelerating_Simulators/#slide-14) |
| PyO3 and maturin | PyO3 generates the CPython bindings for Rust functions marked #[pyfunction]; maturin builds and installs them as a Python wheel, alongside any pure-Python code. | [SimEng 02 · PyO3 and maturin in practice](https://brendanjameslynskey.github.io/SimEng_02_Rust_Python_PyO3/#slide-03); [SimEng 02 · project layout](https://brendanjameslynskey.github.io/SimEng_02_Rust_Python_PyO3/#slide-02) |
| The language boundary | Every call from Python into Rust converts its arguments and results. A good boundary is coarse (one call per simulation) and plain (numbers, tuples, strings), and its cost is measured. | [SimEng 02 · what crosses the boundary](https://brendanjameslynskey.github.io/SimEng_02_Rust_Python_PyO3/#slide-04) |
| The GIL and releasing it | CPython's global interpreter lock lets one thread run Python at a time. Rust code that touches no Python objects can release it (py.detach, formerly allow_threads), so Python threads run simulations in parallel. | [SimEng 02 · releasing the GIL](https://brendanjameslynskey.github.io/SimEng_02_Rust_Python_PyO3/#slide-05) |
| Bit-exact parity | Two implementations that produce identical floating-point results, bit for bit. It requires the same operations in the same order, the same event order and the same library functions, and it turns any discrepancy into a located bug. | [SimEng 02 · the parity checklist](https://brendanjameslynskey.github.io/SimEng_02_Rust_Python_PyO3/#slide-06); [SimEng 02 · three traps that cost one ulp](https://brendanjameslynskey.github.io/SimEng_02_Rust_Python_PyO3/#slide-08); [SimEng 03 · the same order in C++](https://brendanjameslynskey.github.io/SimEng_03_SystemC_TLM_Models/#slide-02) |
| Correctly rounded summation (math.fsum) | math.fsum returns the exactly rounded sum of its inputs; statistics.fmean uses it. A plain loop accumulates rounding error, so a port must reproduce the algorithm, not just add. | [SimEng 02 · three traps that cost one ulp](https://brendanjameslynskey.github.io/SimEng_02_Rust_Python_PyO3/#slide-08) |
| MT19937 and Python's random module | CPython's generator is the Mersenne Twister, seeded with init_by_array; random() combines two 32-bit outputs into a 53-bit float, and the variates are written in Python, so the whole stream can be reproduced exactly. | [SimEng 02 · reproducing Python's random numbers](https://brendanjameslynskey.github.io/SimEng_02_Rust_Python_PyO3/#slide-07) |
| abi3 wheels | Extension modules built against CPython's stable ABI work on every later Python version, so one wheel per platform suffices. The free-threaded build has its own ABI and is not covered. | [SimEng 02 · packaging and CI](https://brendanjameslynskey.github.io/SimEng_02_Rust_Python_PyO3/#slide-12) |
| Modern C++ for models | Plain C++17 value types, RAII and lambdas for the model's data and arithmetic, kept free of the simulation kernel so it can be unit-tested alone and ported from a reference in the same floating-point order. | [SimEng 03 · modern C++ for models](https://brendanjameslynskey.github.io/SimEng_03_SystemC_TLM_Models/#slide-02) |
| The SystemC kernel and delta cycles | SystemC (IEEE 1666) runs processes in evaluate/update cycles. Zero-time notifications start another delta cycle at the same simulated time; time advances only when nothing more is runnable. Time is an integer count of a global resolution. | [SimEng 03 · the SystemC kernel](https://brendanjameslynskey.github.io/SimEng_03_SystemC_TLM_Models/#slide-03) |
| Process order and explicit tie-breaks | IEEE 1666 does not specify the order in which processes runnable at the same instant execute, so simultaneous requests for a resource need a tie-break written into the model if results are to be reproducible across kernels. | [SimEng 03 · ties are part of the model](https://brendanjameslynskey.github.io/SimEng_03_SystemC_TLM_Models/#slide-08); [SimEng 01 · ordering floats, breaking ties](https://brendanjameslynskey.github.io/SimEng_01_Rust_for_Simulation_Engineers/#slide-03) |
| TLM-2.0 generic payload and sockets | TLM-2.0 replaces pin-level signals with function calls through initiator and target sockets, carrying a generic payload (command, address, data pointer and length, response) and optional extensions, so models from different sources interoperate. | [SimEng 03 · payloads, sockets and coding styles](https://brendanjameslynskey.github.io/SimEng_03_SystemC_TLM_Models/#slide-05) |
| Approximately timed (AT) and the base protocol | AT models use non-blocking transport with four phases (BEGIN_REQ, END_REQ, BEGIN_RESP, END_RESP), each at its own simulated time, so contention resolves in time order. Accurate, at the cost of a context switch per phase. | [SimEng 03 · the four-phase protocol](https://brendanjameslynskey.github.io/SimEng_03_SystemC_TLM_Models/#slide-06) |
| Loosely timed (LT) and temporal decoupling | LT models use one blocking b_transport call whose delay argument carries timing. Processes run ahead of simulated time by up to a global quantum and synchronise rarely: faster, but resources get booked out of time order. | [SimEng 03 · temporal decoupling and the quantum](https://brendanjameslynskey.github.io/SimEng_03_SystemC_TLM_Models/#slide-07); [SimEng 03 · interactive: the quantum trade-off](https://brendanjameslynskey.github.io/SimEng_03_SystemC_TLM_Models/#slide-10) |
| Global quantum | The longest a loosely-timed process may run ahead of the kernel's time before it must synchronise (tlm_quantumkeeper). Larger quanta mean fewer context switches and larger timing errors. | [SimEng 03 · interactive: the quantum trade-off](https://brendanjameslynskey.github.io/SimEng_03_SystemC_TLM_Models/#slide-10) |
| One elaboration per process | A SystemC program elaborates its module hierarchy and calls sc_start once; tests that each run a simulation therefore fork a child per test. | [SimEng 03 · GoogleTest and sanitizers](https://brendanjameslynskey.github.io/SimEng_03_SystemC_TLM_Models/#slide-11) |
| “Bandwidth × efficiency” | Modelling memory as peak bandwidth times a fixed derating factor. The achieved fraction of peak depends on access pattern, controller, address mapping and load, so a single factor is right for at most one of them. | [SimEng 04 · why bandwidth times efficiency fails](https://brendanjameslynskey.github.io/SimEng_04_Memory_Systems_DRAM_HBM/#slide-01); [SimEng 04 · plugging it into the FHE simulator](https://brendanjameslynskey.github.io/SimEng_04_Memory_Systems_DRAM_HBM/#slide-12) |
| Channels, ranks, bank groups, banks and rows | A DRAM channel has ranks of chips; each rank has bank groups of banks; each bank is an array of rows read through one row buffer. Banks work in parallel; accesses within a bank group must be further apart than across groups. | [SimEng 04 · how DRAM is organised](https://brendanjameslynskey.github.io/SimEng_04_Memory_Systems_DRAM_HBM/#slide-02) |
| DRAM commands and timing parameters | ACT, RD/WR, PRE and REF, separated by minimum gaps such as tRCD, tRP, tCL, tRAS, tRC, tRRD, tCCD, tWTR, tWR and tRTP, defined per speed bin by the JEDEC standards. | [SimEng 04 · commands and timing parameters](https://brendanjameslynskey.github.io/SimEng_04_Memory_Systems_DRAM_HBM/#slide-03) |
| Row hits, misses and conflicts | A hit finds its row open (CL); a miss finds the bank closed (tRCD + CL); a conflict finds another row open (tRP + tRCD + CL). A controller's main job is turning conflicts into hits. | [SimEng 04 · row hits, misses and conflicts](https://brendanjameslynskey.github.io/SimEng_04_Memory_Systems_DRAM_HBM/#slide-04) |
| FCFS and FR-FCFS scheduling | FCFS serves requests in arrival order. FR-FCFS (Rixner et al., 2000) issues ready row hits first, then the oldest ready command, overlapping row opening in some banks with transfers in others. | [SimEng 04 · scheduling and page policy](https://brendanjameslynskey.github.io/SimEng_04_Memory_Systems_DRAM_HBM/#slide-05) |
| Open and closed page policy | Open page leaves a row open after an access, betting on a hit; closed page precharges at once (auto-precharge), betting on a miss rather than a conflict. | [SimEng 04 · scheduling and page policy](https://brendanjameslynskey.github.io/SimEng_04_Memory_Systems_DRAM_HBM/#slide-05) |
| Address mapping and XOR bank hashing | Which address bits select channel, bank group, bank, row and column decides which patterns spread across banks. XOR hashing mixes row bits into the bank index so row-sized strides stop hitting one bank. | [SimEng 04 · address mapping](https://brendanjameslynskey.github.io/SimEng_04_Memory_Systems_DRAM_HBM/#slide-06) |
| Refresh (tREFI, tRFC) | Every tREFI a rank closes its banks and refreshes for tRFC, costing a stream about tRFC/tREFI of its bandwidth and setting the latency tail. | [SimEng 04 · refresh and the four-activate window](https://brendanjameslynskey.github.io/SimEng_04_Memory_Systems_DRAM_HBM/#slide-07); [SimEng 04 · load and latency](https://brendanjameslynskey.github.io/SimEng_04_Memory_Systems_DRAM_HBM/#slide-09) |
| The four-activate window (tFAW) | At most four ACTs per rank in any window of tFAW, a limit on peak current. It caps random traffic, which needs one ACT per access, at 4 (BL/2) / tFAW of peak. | [SimEng 04 · refresh and the four-activate window](https://brendanjameslynskey.github.io/SimEng_04_Memory_Systems_DRAM_HBM/#slide-07) |
| Independent protocol checker | A checker that replays a controller's command log and verifies every timing rule directly, sharing no code with the controller; with property-based traces it is the oracle that finds scheduling bugs. | [SimEng 04 · how we know the model is right](https://brendanjameslynskey.github.io/SimEng_04_Memory_Systems_DRAM_HBM/#slide-10) |
| Cross-checking against another simulator | Running identical traces and parameters through an independent simulator (here DRAMsim3). Agreement where the physics dominates and disagreement where the designs differ both carry information. | [SimEng 04 · cross-checked against DRAMsim3](https://brendanjameslynskey.github.io/SimEng_04_Memory_Systems_DRAM_HBM/#slide-11) |
| Golden model and bit-accurate model | The golden model says what the hardware must compute (here the FHE simulator's NTT); a bit-accurate model mirrors the RTL's internal steps so a scoreboard can check them. | [SimEng 05 · two golden models and a scoreboard](https://brendanjameslynskey.github.io/SimEng_05_Verification_Bridge_cocotb/#slide-04) |
| Scoreboard | The testbench component that predicts each expected output from the model and compares it with what the monitor observed from the design. | [SimEng 05 · two golden models and a scoreboard](https://brendanjameslynskey.github.io/SimEng_05_Verification_Bridge_cocotb/#slide-04) |
| Transactors (driver and monitor) | Testbench components that turn transactions into pin activity and back. A ready/valid handshake must be sampled in the cycle it happens, not after the edge that commits it. | [SimEng 05 · transactors](https://brendanjameslynskey.github.io/SimEng_05_Verification_Bridge_cocotb/#slide-05); [SimEng 05 · cocotb in one page](https://brendanjameslynskey.github.io/SimEng_05_Verification_Bridge_cocotb/#slide-03) |
| Constrained-random stimulus | Random stimulus biased towards corners (0, 1, q - 1, near-maximal operands) while still covering the whole range, so rare situations occur often enough to test. | [SimEng 05 · constrained-random stimulus](https://brendanjameslynskey.github.io/SimEng_05_Verification_Bridge_cocotb/#slide-06); [SimEng 05 · interactive: coverage closure](https://brendanjameslynskey.github.io/SimEng_05_Verification_Bridge_cocotb/#slide-08) |
| Coverage crosses and observability | A cross counts combinations of bins. Reaching a corner is not enough if later logic masks a bug there; the cross with the condition that makes the bug visible is the bin that matters. | [SimEng 05 · functional coverage and crosses](https://brendanjameslynskey.github.io/SimEng_05_Verification_Bridge_cocotb/#slide-07); [SimEng 05 · a seeded bug](https://brendanjameslynskey.github.io/SimEng_05_Verification_Bridge_cocotb/#slide-09) |
| Seeded bugs | Deliberately injected faults (here a missing Barrett correction behind a define) used to check that a testbench can catch them: mutation testing for hardware. | [SimEng 05 · a seeded bug: caught or escaped](https://brendanjameslynskey.github.io/SimEng_05_Verification_Bridge_cocotb/#slide-09) |
| Verilator and Icarus Verilog | Verilator compiles synthesisable SystemVerilog to fast two-state C++ and lints it; Icarus is a four-state event-driven simulator. Running tests on both catches simulator-dependent behaviour. | [SimEng 05 · Verilator, Icarus and CI for RTL](https://brendanjameslynskey.github.io/SimEng_05_Verification_Bridge_cocotb/#slide-10) |
| Cycle models from RTL | A closed-form cycle count (here log2 n (n/2P + 6)) fitted to and checked against every RTL measurement, so it can be trusted to extrapolate to sizes too large to simulate. | [SimEng 05 · RTL cycle counts and a cycle model](https://brendanjameslynskey.github.io/SimEng_05_Verification_Bridge_cocotb/#slide-11) |
| Calibrating a simulator from RTL | Derating the architecture simulator's ideal unit throughput by the efficiency the RTL achieves; it can change which resource the simulator calls the bottleneck. | [SimEng 05 · feeding the RTL back into the simulator](https://brendanjameslynskey.github.io/SimEng_05_Verification_Bridge_cocotb/#slide-12) |
| Switching activity (toggle counts) | The number of bit changes per cycle on a design's nets or registers; activity times capacitance times V squared times f gives dynamic power, so toggle counts are an early power proxy. | [SimEng 05 · switching activity as a power proxy](https://brendanjameslynskey.github.io/SimEng_05_Verification_Bridge_cocotb/#slide-13) |
| pytest fixtures and scopes | Functions that provide what a test needs, requested by naming them as parameters, defined in conftest.py for sharing, and cached per function, module or session. | [SimEng 06 · pytest I](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-02) |
| parametrize and markers | @pytest.mark.parametrize runs one test body over many inputs; markers label tests (slow, nightly) so -m can select them; a strict xfail records a known limitation. | [SimEng 06 · pytest II](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-03) |
| pytest-xdist | A pytest plugin that runs tests in parallel worker processes (-n auto). Tests must be independent: no shared files or global state. | [SimEng 06 · pytest II](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-03) |
| Shrinking | When a property-based test fails, the framework searches for simpler inputs that still fail and reports the simplest it finds, which is usually a readable reproduction of the bug. | [SimEng 06 · properties and shrinking](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-04); [SimEng 06 · stateful testing](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-05) |
| Stateful property testing | Hypothesis generates random sequences of operations (rules) and compares the system with a simple model after every step; failures shrink to a minimal sequence. | [SimEng 06 · Hypothesis: stateful testing](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-05) |
| proptest | Rust's property-based testing library: strategies generate inputs, failures shrink, and failing seeds are saved in proptest-regressions/ and replayed first. | [SimEng 06 · cargo test and proptest](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-11); [SimEng 01 · testing in Rust](https://brendanjameslynskey.github.io/SimEng_01_Rust_for_Simulation_Engineers/#slide-12) |
| Golden tests and re-blessing | Store the output of a reference run and fail when today's differs; re-bless (rewrite the stored output) deliberately, with the diff reviewed alongside the change that caused it. | [SimEng 06 · golden tests and re-blessing](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-06); [SimEng 02 · golden files across languages](https://brendanjameslynskey.github.io/SimEng_02_Rust_Python_PyO3/#slide-09) |
| GoogleTest | The common C++ test framework: TEST, fixtures with TEST_F, value-parameterised TEST_P, EXPECT_* (continue) and ASSERT_* (stop), death tests. | [SimEng 06 · GoogleTest for C++ models](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-10); [SimEng 03 · GoogleTest and sanitizers](https://brendanjameslynskey.github.io/SimEng_03_SystemC_TLM_Models/#slide-11) |
| Sanitizers (ASan, UBSan) | Compiler instrumentation that turns memory errors (AddressSanitizer) and undefined behaviour (UndefinedBehaviorSanitizer) into immediate failures with a stack trace. Build C++ tests with them. | [SimEng 06 · GoogleTest for C++ models](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-10); [SimEng 03 · GoogleTest and sanitizers](https://brendanjameslynskey.github.io/SimEng_03_SystemC_TLM_Models/#slide-11) |
| cocotb | A framework for writing RTL testbenches in Python coroutines that drive an HDL simulator (Icarus, Verilator and others), so a Python model can check the hardware. | [SimEng 06 · cocotb: Python testbenches for RTL](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-12); [SimEng 05 · cocotb in one page](https://brendanjameslynskey.github.io/SimEng_05_Verification_Bridge_cocotb/#slide-03) |
| Functional coverage | Bins describing the situations a testbench must exercise (a wrap-around, a boundary value), counted during the run; an empty bin is a hole in the verification, whatever the code coverage says. | [SimEng 06 · cocotb](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-12); [SimEng 05 · functional coverage and crosses](https://brendanjameslynskey.github.io/SimEng_05_Verification_Bridge_cocotb/#slide-07) |
| Mutation testing | Make small deliberate bugs (mutants) in the code and run the tests against each: a killed mutant was noticed, a surviving one was not. The mutation score measures how much the tests actually check. | [SimEng 06 · mutation testing](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-07); [SimEng 06 · interactive: mutation score versus coverage](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-08) |
| Equivalent mutants | Mutants that change the code but not its behaviour, so no test can kill them; survivors must be triaged rather than all chased. | [SimEng 06 · coverage, and what it does not tell you](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-09) |
| Line, branch and region coverage | The fraction of lines, branch outcomes or code regions that the tests execute. Low coverage is a warning; high coverage does not show that results are checked. | [SimEng 06 · coverage, and what it does not tell you](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-09); [SimEng 06 · interactive](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-08) |
| MC/DC | Modified condition/decision coverage: each condition in a decision must be shown to change the outcome independently. DO-178C requires it for the most critical avionics software. | [SimEng 06 · coverage, and what it does not tell you](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-09) |
| JUnit XML and Cobertura reports | The de facto interchange formats for test results and coverage, written by pytest, cargo-nextest, GoogleTest and cocotb, and read by Jenkins and most CI systems. | [SimEng 06 · running it all in CI](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-13) |
| Performance-regression gate | A CI step that benchmarks the build and fails it if a benchmark is slower than a stored baseline by more than a set margin. | [SimEng 06 · running it all in CI](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-13); [SimEng 01 · criterion](https://brendanjameslynskey.github.io/SimEng_01_Rust_for_Simulation_Engineers/#slide-11); [SimEng 05 · an exact cycle-count gate](https://brendanjameslynskey.github.io/SimEng_05_Verification_Bridge_cocotb/#slide-10) |
| Flaky tests | Tests that pass or fail without a code change. In a deterministic simulator they point to shared state, an unseeded random number or a wall-clock dependency, and should be fixed, not retried. | [SimEng 06 · running it all in CI](https://brendanjameslynskey.github.io/SimEng_06_Testing_Frameworks/#slide-13) |
| Discrete-event simulation (DES) | A simulator whose state changes only at instants (events). A clock, a state, a time-ordered event list and handlers; the clock jumps from one event to the next (next-event time advance), so idle time costs nothing. | [LLM Inference Simulators glossary](https://brendanjameslynskey.github.io/LLM_Hub_Inference_Simulators/#g-des) |
| SimPy | A small, pure-Python DES library: Environment, processes, timeouts, events, Resource, Container, Store and interrupts. It has no built-in statistics or tracing; the probes are yours to design. | [LLM Inference Simulators glossary](https://brendanjameslynskey.github.io/LLM_Hub_Inference_Simulators/#g-simpy) |
| Process interaction and coroutines | Writing each entity's life as one sequential function that suspends while it waits, instead of scattering it over event handlers. Python generators make this natural: yield an event, resume when it fires. | [LLM Inference Simulators glossary](https://brendanjameslynskey.github.io/LLM_Hub_Inference_Simulators/#g-process) |
| Determinism, tie-breaking and RNG streams | Same configuration and seed must give bit-identical results: break ties between simultaneous events with a sequence number, prefer integer time for clocked models, and give each component its own random stream. | [LLM Inference Simulators glossary](https://brendanjameslynskey.github.io/LLM_Hub_Inference_Simulators/#g-determinism) |
| Cost model | The part of a simulator that answers "how long does this take?" (and, with a power model, "how many joules?"). Kept separate from the event engine so a roofline can later be replaced by a measured table or an RTL-calibrated model. | [LLM Inference Simulators glossary](https://brendanjameslynskey.github.io/LLM_Hub_Inference_Simulators/#g-costmodel) |
| Queueing theory checks (M/M/1, M/D/1) | Closed-form results that a simulator's engine must reproduce: M/M/1 mean time in system 1/(μ−λ); M/D/1 mean wait λS²/(2(1−ρ)) (Pollaczek–Khinchine). The KV link is tested this way. | [LLM Inference Simulators glossary](https://brendanjameslynskey.github.io/LLM_Hub_Inference_Simulators/#g-queueing) |
| Little's law and the operational laws | L = λW: mean population equals arrival rate times mean time in system, for any stable system. With the utilisation and forced-flow laws it gives free consistency checks on a simulator's probes. | [LLM Inference Simulators glossary](https://brendanjameslynskey.github.io/LLM_Hub_Inference_Simulators/#g-little) |
| The verification ladder | Layers of evidence: unit tests against hand calculations, invariants, analytic checks, behavioural expectations, property-based tests, differential tests and, finally, correlation against measurement. | [LLM Inference Simulators glossary](https://brendanjameslynskey.github.io/LLM_Hub_Inference_Simulators/#g-ladder) |
| Property-based testing (Hypothesis) | Generate many random configurations and check that invariants hold for all of them; Hypothesis shrinks any failure to a minimal example. | [LLM Inference Simulators glossary](https://brendanjameslynskey.github.io/LLM_Hub_Inference_Simulators/#g-hypothesis) |
| Differential testing | Requiring two independent implementations to agree exactly on the same input: here the fast path against the baseline, and the browser JavaScript against the Python simulator. | [LLM Inference Simulators glossary](https://brendanjameslynskey.github.io/LLM_Hub_Inference_Simulators/#g-differential) |
| Profiling a simulator | Measure before optimising (cProfile, py-spy, perf). Time usually goes to model code that runs per entity per step, not to the event kernel. | [LLM Inference Simulators glossary](https://brendanjameslynskey.github.io/LLM_Hub_Inference_Simulators/#g-profiling) |
| Parallel runs and Amdahl's law | Independent runs parallelise trivially (processes, job arrays), but each technique only speeds up the share of time it touches; serial overheads cap the gain. | [LLM Inference Simulators glossary](https://brendanjameslynskey.github.io/LLM_Hub_Inference_Simulators/#g-parallelruns) |
| CI, golden metrics and engineering metrics | Run tests on every push and sweeps nightly (Jenkins or similar); fail the build if golden metrics drift; track correlation error, coverage, simulator speed and test health as engineering metrics. | [LLM Inference Simulators glossary](https://brendanjameslynskey.github.io/LLM_Hub_Inference_Simulators/#g-ci) |
| Transaction-level modelling (SystemC TLM-2.0) | Modelling bus reads and writes as function calls with annotated delays rather than signal wiggles. Loosely-timed TLM boots software; approximately-timed TLM models contention. The industry route to virtual platforms. | [LLM Inference Simulators glossary](https://brendanjameslynskey.github.io/LLM_Hub_Inference_Simulators/#g-tlm) |
| RTL simulation, co-simulation and golden models | The software model is the executable specification and the golden reference (a scoreboard in the RTL testbench). RTL cycle counts calibrate the model, workload traces become directed tests, and co-simulation embeds RTL blocks in the system model. | [LLM Inference Simulators glossary](https://brendanjameslynskey.github.io/LLM_Hub_Inference_Simulators/#g-cosim) |
| RTL power and thermal analysis | Switching activity from RTL simulation or emulation, run on real workload traces, gives per-block energies that calibrate the simulator; power maps feed thermal models that find thermal hot-spots. | [LLM Inference Simulators glossary](https://brendanjameslynskey.github.io/LLM_Hub_Inference_Simulators/#g-rtlpower) |
| Percentiles and tail-latency CCDFs | Report p50, p90 and p99, not means, and plot the fraction of samples slower than x on log-log axes, where tails show. Say which population (all tokens or per request), and use streaming sketches when samples are many. | [LLM Inference Simulators glossary](https://brendanjameslynskey.github.io/LLM_Hub_Inference_Simulators/#g-percentiles) |
| Number-theoretic transform (NTT) | The FFT over a finite field Zq. It moves a limb between coefficient and evaluation form in (N/2) log N butterflies, so polynomial multiplication becomes element-wise. Every key switch and rescale runs NTTs. | [FHE Accelerator Simulators glossary](https://brendanjameslynskey.github.io/FHE_Hub_Accelerator_Simulators/#g-ntt) |
| Modular reduction (Barrett, Montgomery) | Ways to compute a·b mod q without division, using precomputed constants. Every butterfly and multiply-add lane in an FHE accelerator contains one. | [FHE Accelerator Simulators glossary](https://brendanjameslynskey.github.io/FHE_Hub_Accelerator_Simulators/#g-modred) |
| HBM and key streaming | Off-chip high-bandwidth memory. Evaluation keys and DFT plaintexts are too big to keep on chip, so they stream from HBM, which is why bootstrapping is often memory-bound. | [FHE Accelerator Simulators glossary](https://brendanjameslynskey.github.io/FHE_Hub_Accelerator_Simulators/#g-hbm) |
| NTT-, MAC-, memory- and power-bound | The simulator's verdict: the most-utilised resource sets the bound (HBM, NTT units, multiply-add lanes), or power when the power limit throttles a compute-bound design. | [FHE Accelerator Simulators glossary](https://brendanjameslynskey.github.io/FHE_Hub_Accelerator_Simulators/#g-bound) |
| Kernel-level trace | The contract between a scheme model or compiler and the hardware model: HE operations with their inputs, outputs, keys, plaintexts, levels and primitive kernels. | [FHE Accelerator Simulators glossary](https://brendanjameslynskey.github.io/FHE_Hub_Accelerator_Simulators/#g-trace) |
| Scratchpad, LRU and spills | The accelerator's on-chip SRAM, modelled as a least-recently-used store of ciphertexts, keys and plaintexts. A miss loads from HBM; evicting a live ciphertext writes it back (a spill). | [FHE Accelerator Simulators glossary](https://brendanjameslynskey.github.io/FHE_Hub_Accelerator_Simulators/#g-scratchpad) |
| Calibration and out-of-sample prediction | Fit as few model coefficients as possible to measurements (here, one rate to an OpenFHE multiplication), then judge the model on quantities it was not fitted to. | [FHE Accelerator Simulators glossary](https://brendanjameslynskey.github.io/FHE_Hub_Accelerator_Simulators/#g-calibration) |
| Key switching and evaluation keys | After a multiplication (relinearisation) or a rotation, part of the ciphertext is under the wrong key; key switching fixes it using an evaluation key (78–210 MiB for the N = 216 sets used here). It dominates the cost of FHE. | [FHE Accelerator Simulators glossary](https://brendanjameslynskey.github.io/FHE_Hub_Accelerator_Simulators/#g-keyswitch) |
